\subsection{Método da busca}
\label{subsec:control-repos-method}

Para situar a biblioteca Aule como veículo, dentre o que já existia na comunidade open-source, foi realizada uma pesquina no Github de repositórios relacionados com sistemas de controle e controladores PID, para verificar quais opções existiam e qual era a maturidade desses repositorios. Perceba que apesar de não ser uma revisão sistemática, o método dessa pesquisa é reprodutível através dos critérios apresentados nos paragrafos seguintes.

No github foram realizadas duas buscas, ambas filtrandas por \texttt{language:rust}, com as seguintes palavras chave: \texttt{pid} e \texttt{"control system"}, onde a última é pesquisada pela frase exata. A ordenação da lista de repositórios encontrados com essas palavras chave, foi através do números de estrelas, pois isso traz primeiro os repositorios nos quais a comunidade open-source mais creditou relevancia. Note que isso não tem relação com a maturidade ou qualidade do repositório, apenas indica que diversas pessoas viram o trabalho presente no repositório e deu crédito ao que foi implementado ali. Para evitar de adicionar na lista novos repositórios toda semana, pois toda semana surge novos repositórios no Github, foi definida uma data de congelamento desta lista: 9 de Junho de 2025. Cada repositório encontrado, sendo ele uma biblioteca (lib) ou um binário (bin) foi adicionado a lista, sendo a ordem de grandeza dessa lista de centenas. Com isso, se fez necessário realizar uma curadoria manual para reduzir o número de repositórios, tanto pela relevância quanto por falso positivos.

O primeiro critério para a eliminação de repositórios foi ter pelo menos 1 estrela. Isso elimina repositórios de teste e com pouca divulgação. Após esse corte feito em ambas as buscas os números caíram de 340 para 165, na palavra chave \texttt{pid}, e de 347 para 125, na frase exata \texttt{"control system"}. Após isso, foi realizada uma verificação de falsos positivos manualmente. Para a busca da palavra chave \texttt{pid} foi removido repositórios relacionados com Process Identifier do linux e outros não relacionados (ou irrelevantes), enquanto para a busca pela frase exata \texttt{"control system"}, foi removido o que não estava relacionado com sistemas de controle, por exemplo: version control ou source control. Depois desta etapa, a lista \texttt{pid} saiu de 165 para 59 e a lista de \texttt{"control system"} saiu de 125 para 6. Note que a diminuição da lista \texttt{"control system"} foi de aproximadamente 95\%. Isso se deve a colisão de "control" com o controle de versão, gerando muitos falso positivos.

Para analisar a qualidade e maturidade de cada repositório, foi adotada um método de classificação diferente para cada uma das listas: na lista PID, foi feita uma grade de 18 atributos:

\begin{enumerate}
  \item embedded setpoint: A referência está embarcada no controlador (Sim é um ponto negativo);
  \item mutable setpoint: A referencia pode ser modificada (Sim é um ponto positivo);
  \item mutable kp,ki,kd: Os valores de Kp, Ki e Kd podem ser modificados (Sim é um ponto positivo);
  \item generic typing: Possui tipos genericos (não/primitivo/completo);
  \item anti-windup: Possui anti-windup no controlador PID (Sim é um ponto positivo);
  \item output-limit: Pode limitar o sinal de controle do PID (Sim é um ponto positivo);
  \item Deadband: Ignora o erro dentro da banda (Sim é um ponto positivo);
  \item no\_std: Oferece suporte a no\_std (Sim é um ponto positivo);
  \item library/binary: o crate é uma biblioteca ou um binário;
  \item Documentation: tem documentação substantiva (Sim é um ponto positivo);
  \item Statistics: Possui medição de estatísticas do controlador (Sim é um ponto positivo);
  \item CI: Possui pipelines de Continuous Integration (Sim é um ponto positivo);
  \item crates.io: Foi publicado no crates.io (Sim é um ponto positivo);
  \item tests: Possui testes automatizados (Sim é um ponto positivo);
  \item Plot: Possui geração de gráficos ou plots (Sim é um ponto positivo);
  \item benches: Tem benchmarks (Sim é um ponto positivo);
  \item examples: Tem exemplos de como utilizar a biblioteca (Sim é um ponto positivo);
  \item RK4 integrator: Possui suporte ao integrador Runge-Kutta 4 (Sim é um ponto positivo).
\end{enumerate}

Enquanto isso, na lista "control system", foi feita uma inspeção no código para buscar características descritivas, ao invés de avaliação binária de sim/não. Estas características são:

\begin{enumerate}
  \item no\_std: Compila sem std e pode ser utilizado em sistemas embarcados;
  \item genéricos: Genérico em tipo numérico e em que grau (nenhum, f32-f64, pleno);
  \item backend: Qual crate de algebra linear foi utilizado (nalgebra, faer, ndarray, caseiro, nenhum). Além disso é avaliado se a algebra linear pode ser utilizada em sistemas embarcados;
  \item capacidades: Quais recursos de controle são implementados (TF, SS, discreto, solver ODE, laço de simulação, controlador, identificação, análise em frequência, filtros, c2d);
  \item abstração: Como sistemas são modelados (ou compostos) (matrizes A-B-C-D, álgebra de TF, composição type-safe, diagrama de blocos ou grafo, composição direta (forward), nenhuma);
  \item concorrência: Trata concorrencia ou data races (threads, Send/Sync, atômicos, tempo real);
  \item maturidade: indicativos de estrelas, atividade recente, downloads no crates.io (e se está lá), possui documentação, possui CI, possui testes.
\end{enumerate}

Note que a busca no Github é diferente de uma base indexada, pois a quantidade de estrelas muda de acordo com as datas, além de palavras chaves excluírem repositórios que não citam o nome (por exemplo PID), mas implementam a funcionalidade. Na próxima subseção \ref{subsec:control-repos-table} é realizada a comparação e analise dos repositórios encontrados com estes métodos.

\section{Estado atual da biblioteca Aule}
\label{sec:aule-state}

Para instanciar os padrões descritos na taxonomia, em algoritmos de controle, se faz necessário ter um veículo. Ou seja, uma forma de implementar os algoritmos de controle que possua os padrões de data race. Neste trabalho é utilizada a biblioteca de controle Aule, pois além de prover blocos básicos de controle, como entradas, saídas, algoritmos de controle, função de transferencia e espaço de estados, também herda e preserva (da linguagem Rust) o código no lado safe, de forma estática e sem heap, com a composiçao forward de blocos.

Um ponto importante sobre a biblioteca Aule é sobre ela ser uma biblioteca e não um framework. A diferença entre os dois está no conceito de Inversion of Control \cite{martin-fowler:inversion-of-control, johnson1988reusable}, onde é feita a pergunta: quem chama quem?. Pois em um framework, o código do usuário é chamado pelo framework, facilitando a construção em casos específicos, mas diminuindo a flexibilidade em geral. No caso da biblioteca, o código da biblioteca é chamado pelo usuário, mantendo o controle do fluxo nas mãos dele. Isso aumenta a flexibilidade, entretanto joga a responsabilidade para o usuário implementar mais código para o controle do fluxo. Essa decisão foi tomada, pois permite o usuário criar códigos mais complexos a partir de blocos simples (providos pela biblioteca Aule), como por exemplo: a biblioteca Aule, não precisa fornecer um bloco de rede neural, basta o usuário usar o crate da sua escolha e implementar o trait \texttt{Block} da Aule.

Além do fato de ser uma biblioteca, a Aule também é construida em cima dos conceitos de \texttt{no\_std} first e feature-gating, para permitir o uso em qualquer plataforma que suporte a funcionalidade. \texttt{no\_std} first, implica que toda funcionalidade é implementada inicialmente somente com o \texttt{core} que a linguagem Rust provê. Isso permite o o máximo de funcionalidades em plataformas que não possuem \texttt{std}, como embarcados e webassembly. Caso alguma funcionalidade ainda precise de \texttt{alloc} (para alocação dinamica) ou \texttt{std} (para recursos do Sistema Operacional), essa funcionalidade é exposta através da habilitação de uma feature que pode ser habilitada em tempo de compilação. Isso é necessário, pois o código que não precisar dessa funcionalidade não precisa importar ela da biblioteca. Habilitar ou desabilitar uma feature em tempo de compilação é chamado de feature-gating. Para permitir um uso ainda maior, todo bloco implementado é pensado em Generics. Entretanto algumas garantias devem ser feitas: então o foco é generics que atendam um desses grupos: Números de ponto flutuante (32 e 64 bits), Números Complexos (32 e 64 bits) e Matrizes (com números de ponto flutuante e números complexos, tanto 32 como 64 bits em ambos os casos).

Hoje na biblioteca Aule, existem as seguintes funcionalidades implementadas: estruturas básicas da integração de blocos, como: trait Block para implementar blocos; struct Signal, para representar os dados passados entre um bloco e outro; e struct Simulation e EndlessSimulation, para gerar estados de tempo para alimentar a struct Signal. Note que o EndlessSimulation, pode ser usado mesmo fora de simulação para gerar os tempos sem um limite final. Também é implementada na biblioteca representações de sistemas SISO: Tf (Transfer Function), SS (State Space), DTf (Discrete Transfer Function) e DSS (Discrete State Space). Também estão implementados métodos de identificação de sistemas de primeira e segunda ordem, como: Smith, Ziegler-Nichols, Mollenkamp, Hagglund e SundaresanKrishnaswamy.

Outros blocos também são implementados, mas divididos em tiers, sendo: tier1 que contém blocos que não possuem outros blocos dentro dele; tier2 com blocos que são construídos com a composição de outros blocos; e tier3 onde são blocos de simulação inteiros dentro dele. Com isso, cada chamada de um bloco da tier1 é apenas lógica do bloco dentro dela. No bloco da tier2, cada chamada do bloco envolve chamar outros blocos em cascata. E na tier3 a chamada envolve chamar toda uma simulação, e não só um passo da simulação. A tier 3 atualmente está vazia e na tier2 existe somente o preditor Smith.

Na tier1 é onde se concentra a maior parte dos blocos implementados. Uma por que são blocos mais simples de serem implementados e outra por serem a base para a construção dos outros blocos (incluindo blocos do usuário). Dentre eles estão os segintes blocos:

\begin{description}
  \item[Métricas] IAE, ISE, ITAE e Good Hart;
  \item[Entrada] Impulso, Degrau, Rampa, Dente de Serra, Onda Quadrada e Senoidal, além de um bloco para ler dados de um CSV e transformar em um \texttt{Signal};
  \item[Saída] writter (para escrever em um CSV), printer (para mostrar no stdout) e plotter (para mostrar em um gráfico);
  \item[Filtro de primeira ordem] passa-baixa e passa-alta;
  \item[Filtro de segunda ordem] passa-faixa e rejeita-faixa;
  \item[Condicionamento de sinal] delay (para adicionar um atraso ao sinal) e saturation (para limitar o valor do sinal);
  \item[Controlador] PID com anti-windup embutido;
  \item[Interação com embarcados] ponte SWD;
\end{description}

Sobre os blocos de sincronização, estes estão em desenvolvimento (ver \ref{cap:cron}). Atualmente a bilblioteca Aule está madura para simulações e implementações de algoritmos de controle, entrentanto ainda existe lacunas que serão cobertas até a dissertação \ref{cap:cron} e lacunas que não possuem prioridades no momento (como analise em frequencia).

\section{Caso demonstrativo: setpoint escalar compartilhado (P1)}
\label{sec:case-setpoint}

% 5.2.1
\subsection{Cenário e o padrão P1}
\label{subsec:setpoint-scenario}

Nesta seção será apresentado um caso de compartilhamento de um escalar entre duas tarefas. Esse dado compartilhado é uma referência, cujo controlador deve perseguir, através do envio de um sinal de controle. Com isso, uma tarefa escreve neste valor compartilhado, enquanto a outra, lê este valor. A tarefa responsável por ler o valor é a tarefa de controle, onde o controlador está atuando e precisa desse valor de referência em intervalos fixos de tempo, para conseguir seguir a referência. A tarefa que escreve o valor é uma tarefa de interação com o meio externo (ou com o usuário). Desta forma, esta tarefa recebe um valor de forma assíncrona e precisa escrever esse valor na variável de referência (ou setpoint). Essa forma de interação é comum, pois o usuário pode, por exemplo, alterar o valor de referência em uma IHM, e esse valor é recebido pela tarefa sem aviso ou intervalo definido. É recebido no momento em que o usuário decide alterar. Essa interação pode gerar uma leitura de valor obsoleto na tarefa de controle, pois o acesso ao valor não é indivisível e ordenado.

Note que neste caso, existem: 2 tarefas; um valor compartilhado escalar, por exemplo, a altura de um tanque, ou a velocidade de um motor, ou a temperatura de uma câmara, etc.; e uma tarefa que se comporta como leitora e outra que se comporta como escritora. Esse caso é mapeado exatamente para o caso P1 da taxonomia (\ref{subsec:taxonomy}), onde o trio é composto por $\langle \text{Tarefa-Tarefa},\text{Escalar},\text{Leitor-Escritor}\rangle$. Note que a referência é um valor escalar, logo ela cabe em uma operação atômica. Isso corta o caso P3. Além disso, o valor atual não depende do valor anterior, o que corta o caso P4.

Visto que a biblioteca Aule é o veículo onde o loop de controle vive, é esperado que ela seja utilizada neste exemplo. Entretanto, ela não será utilizada por 2 motivos que se complementam: o primeiro é que o P1 mora na borda entre a tarefa de comunicação e a tarefa de controle e não no núcleo de controle. Com isso, utilizar Aule, neste caso, não traria ganhos para analisar o caso P1 proposto. Consequentemente, o segundo motivo vem deste, pois usar Aule poderia passar a ideia que a garantia mostrada vem da biblioteca e não da linguagem Rust. Para casos onde realmente existe um algoritmo de controle em execução, como, por exemplo, na planta de controle física, o uso da biblioteca Aule é essencial. Na próxima subseção (\ref{subsec:setpoint-c}) é mostrado o código em C que instancia o caso descrito na subseção atual.

\subsection{O data race em C}
\label{subsec:setpoint-c}

Na listagem \ref{code:data-race-c}, é apresentado o trecho de código em C, que possui o data race apresentado em \ref{subsec:setpoint-scenario}. Neste código a variável \texttt{g\_setpoint} é compartilhada entre a tarefa \texttt{comm\_task} (escritora) e a tarefa \texttt{control\_loop} (leitora). Note que a variável \texttt{g\_setpoint} não possui nenhuma sincronização.

\codec{Data race (P1) de setpoint compartilhado entre leitor-escritor}{code:data-race-c}{src/p1/setpoint.c}

Para que o trecho apresentado seja um data race, ele deve atender a definição de data race, descrita em \ref{sec:dr-def}. Nela, um data race deve possuir: 2 contextos, cumprido com a tarefa leitora e a tarefa escritora; pelo menos 1 escrita, cumprido com a tarefa escritora; acesso não-atômico, cumprido, pois o acesso é direto; e sem happens before, cumprido, pois com o acesso direto não existem restrições para o compilador (ou processador) reordenar as instruções de acesso. Com as quatro condições atendidas, o trecho de código em C configura-se como um data race e note que é o lado indivisível e ordenado do acesso que falha.

Mesmo com o data race presente, o compilador compila sem erro ou aviso e permite que o programa seja executado sem falha aparente. Ou seja, o programa é executado com um bug latente, onde a leitura do valor do controlador pode ser inconsistente e gerando um sinal de controle errado e uma saída não-determinística. Note que esta é a versão ingênua do C, justamente porque esse é o jeito natural de escrever em C e o compilador não impede o desenvolvedor de escrever assim. Para encontrar este data race, é possível executar o sanitizer TSan e confirmar. \subsection{A recusa do compilador em Rust safe}
\label{subsec:setpoint-reject}

Recusar determinísticamente e em tempo de compilação é justamente o que a linguagem Rust faz. Aqui é usado o mesmo cenário da subseção anterior (\ref{subsec:setpoint-c}), instanciando o caso P1: duas tarefas compartilhando um valor, sem sincronização, onde uma é leitora e a outra escritora. É importante salientar que para um valor static ser compartilhado entre duas tarefas, em Rust, é necessário que esse valor seja \texttt{Sync}.

Na listagem \ref{code:setpoint-safe} é apresentado o trecho de código em Rust para este cenário. Esse trecho de código é uma implementação ingenua, onde é implementado uma transposição direta do código implementado em C. Neste código, temos o valor compartilhado na linha 6: um static com o tipo \texttt{Cell<f32>}, esse valor permite uma mutabilidade interior natual, já que em Rust safe não é permitido acessar uma variável mutável e static (que dure todo o lifetime do programa). Para acessar isso é necessário usar blocos unsafe. Da mesma forma que o cenário em C, existem duas tarefas: uma para ler setpoints do usuário, por meio do stdin. Esta é a tarefa escritora, pois recebe o valor do usuário e escreve na variável compartilhada; e a outra tarefa é o loop de controle, a qual lê o valor da variável compartilhada (setpoint) a cada ciclo do controle (tarefa leitora).

\coderust{{Data race (P1) de setpoint compartilhado entre leitor-escritor, em Rust safe e ingênuo}}{code:setpoint-safe}{src/p1/setpoint_safe.rs}

Ao compilar o trecho de código \ref{code:setpoint-safe}, é apresentado um erro de compilação, descrito na listagem \ref{code:rustc-error}. Neste erro de compilação é apresentado o motivo da falha da compilação: o tipo \texttt{Cell<T>} não implementa a trait \texttt{Sync}, logo a variável de setpoint (na linha 6) não pode ser compartilhada entre as tarefas. Isso mostra a recusa do compilador sobre o data race presente no código \ref{code:setpoint-safe}. Note que, o valor possuir 2 acessos concorrentes e sem sincronização fica inexpremível na linguagem Rust, pois o código nem compila. O que é diferente de C, que permite a compilação e execução do código com data race. Perceba também que o problema foi pego em tempo de compilação e não foi necessário exercitar o código, como acontece na detecção em C, com o sanitizer TSan. Isso fornece justamente o que a subseção \ref{subsec:setpoint-c} buscava: uma forma de detectar o problema em tempo de compilação e de forma deterministica, uma vez que não depende de exercitar o código e o resultado do compilador é sempre o mesmo para a mesma entrada (o mesmo código).

% 5.2.4
\subsection{A forma segura com atomic}
\label{subsec:setpoint-atomic}

Na subseção anterior \ref{subsec:setpoint-reject}, é apresentado um trecho de código que instancia em Rust, o padrão P1 da taxonomia. Porém, nesse trecho somente é mostrado a recusa do Rust ao detectar um data race em tempo de compilação. Nesta subseção é mostrado como remover o data race em Rust. Na listagem \ref{code:setpoint-atomic} é apresentado a mudança que torna o trecho de código compilado: mudar o tipo de \texttt{Cell<f32>}, para \texttt{AtomicU32}, na linha 8 e alterar o acesso nas linhas 10, 11, 21, 25, 26 e 30. O motivo da mudança de tipo é porque o tipo \texttt{AtomicU32} é \texttt{Sync}, enquanto o tipo \texttt{Cell<f32>} não o é. Com isso, o \texttt{AtomicU32} pode ser compartilhado entre as tarefas. A mudança de acesso nas linhas 21 e 30 são necessárias por que o \texttt{AtomicU32} exige acesso atomico através dos métodos \texttt{store} e \texttt{load}, indicando a ordem utilizada como argumento. Além disso, nas linhas 10, 11, 25 e 26, são construído \texttt{Arc} para serem movidos para dentro da thread, ao contrário da forma antiga em que as treads recebiam uma referencia imutável do static.

\coderust{{Data race (P1) de setpoint compartilhado entre leitor-escritor, em Rust safe com atomics}}{code:setpoint-atomic}{src/p1/setpoint_atomic.rs}

Note que na linha 8 de \ref{code:setpoint-atomic} o atomic é construído dentro do tipo \texttt{Arc} (Atomically Reference Counted). Foi escolhido implementar desta forma, pois na biblioteca Aule a sincronização entre leitor-escritor será implementada assim. Utilizar \texttt{Arc} ou \texttt{static} funciona da mesma forma, pois ambos geram formas de compartilhamento entre threads: static com referencias imutáveis e \texttt{Arc} com cópias owned das referencias. Outro ponto para se notar é o uso de um atomico inteiro, ao invés de um atomic float (\texttt{AtomicF32}). Isso ocorre, pois a biblioteca padrão do Rust não possui \texttt{AtomicF32}, sendo necessário armazenar os bits do \texttt{f32} em um \texttt{u32} atomico e recupera-lo depois. Poderia ser feito uma struct para facilitar o acesso e evitar erros, sempre interagindo com floats. Entretanto para a simplicidade do exemplo isso não foi feito.

Além do programa agora compilar em Rust, podemos usar a definição de data race \ref{sec:dr-def} e perceber que agora a cláusula de acesso não-atomico não pode ser mais satisfeita, pois o tipo exige o acesso atomico, implicando na eliminação do data race. Isso faz com que o ato de compilar do Rust torne os data races inexprimíveis e não improváveis, pois está removendo uma das condições de data race do código (o acesso não-atomico). Perceba que aqui em Rust é obrigatório a garantia de não-data race, enquanto lá em C, o uso de atomics é opcional. Nesta subseção é mostrada como o data race é resolvido usando o tipo atomico do Rust, entretanto esse tipo não elimina race conditions lógicas.

% 5.2.5
\subsection{Leitura do caso como evidência}
\label{subsec:setpoint-evidence}

As seções \ref{subsec:setpoint-c}, \ref{subsec:setpoint-reject} e \ref{subsec:setpoint-atomic} apresentam um experimento onde são apresentada versões do mesmo padrão (P1 da taxonomia) em três cenários diferentes: C ingênuo, Rust safe ingênuo (transpondo o código em C) e Rust safe com atomics. Como resultado, tem-se que a linguagem C não informa nada nem na compilação e nem na execução do programa, sendo necessário um sanitizer (TSan) para detectar o data race exercitado em tempo de execução. Já a linguagem Rust aponta o data race e o previne, impedindo a compilação. Quando o ajuste é feito, o data race é eliminado por meio da mudança para um tipo atomico. De acordo a subseção \ref{subsec:dim-inst} o trio foi instanciado neste experimento, e de acordo com a subseção \ref{subsec:dim-comp}, a dimensão momento, foi passada de tempo de execução para tempo de compilação. Além disso a dimensão natureza passou de disciplina e sanitizer para verificação por tipos.

Note que o experimento executado pode ser reproduzido com o código presente no repositório \cite{quals-repo}, através da execução do Makefile presente na pasta \texttt{src/p1/}. O resultado do experimento será sempre o mesmo tanto para o Rust e como para o C. Note que saída do experimento se refere a como o data race é detectado e como isso é resolvido. Note que o valor de saída impressso no stdout, pode variar de acordo com o escalonador atual. O que não modifica a saída do experimento. Esse experimento não é arbitrário, pois demonstra o padrão P1 da taxonomia \ref{sec:taxonomy} e foi escolhido por ser o mais simples entre os padrões e ser 100\% safe, sem bordas unsafe, como demonstrado em \ref{sec:border}.

Por último, vale salientar que esse não é um experimento de custo, pois estes serão desenvolvidos na dissertação e não na qualificação. Além disso, esse experimento mostra a eliminação de data races e não race conditions de lógica.

\section{Limitações conhecidas}
\label{sec:partial-limitations}

É importante definir os limites da segurança garantida pela linguagem Rust e também até onde o experimento da qualificação alcançou. Como dito anteriormente, o Rust não possui qualquer garantia sobre condições de corrida lógica, pois isso é definido pela lógica de implementação do desenvolvedor e deve ser resolvido por ele. Por exemplo, o setpoint no experimento descrito em \ref{sec:case-setpoint}, mesmo atomico ainda pode ser lido obsoleto. Além disso, o Rust não protege de problemas de memória que caem fora do memory safety, como: stack overflow, panic e overflow aritimético. Quando se está no mundo de sistemas embarcados, lidar com o hardware sempre será inseguro, independente da linguagem, pois existe a probabilidade de falha nesta interação. Com isso, o HAL e PAC possuem blocos unsafe e é necessário confiar no soundness da implementação desta camada, realizada por outros desenvolvedores.

Além do limite da linguagem Rust, também existe o limite do que foi mostrado no experimento da qualificação, onde foi apresentado somente o padrão P1, sem analise de custo. O custo é importante para a falsificabilidade do experimento, pois a hipotese é: o custo da sincronização safe não é cara o suficiente em comparação a C, a ponto de instabilizar a malha. Com isso, essa hipotese é falsiável pois o custo pode ser maior e medido em experimento. O que se sabe sobre o custo até o momento são informações sobre a MCU (ESP32), como: load e store são baratos e RMW necessita de um laço CAS (Compare-And-Swap). Entretanto ainda é necessário realizar o disassembly do código gerado para a MCU para confirmar qual o custo real. Note que o padrão P2 possui um unsafe residual e ainda precisa entrar nos experimentos, enquanto o padrão P3 será usado para medir custos. Na qualificação, apenas o protocolo dos experimentos são apresentados, deixando a realização destes para a fase de dissertação.

Perceba que ter exercitado somente um padrão (P1) não elimina o fato da rejeição por construção do Rust, através da exigencia de \texttt{Sync} e \texttt{Send}, uma vez que a generalização vem da garantia da linguagem, o padrão P1, serviu para exercitar essa garantia que a linguagem provê. No proximo capitulo (\ref{cap:cron}) é apresentado o cronograma de experimentos e desenvolvimento até a dissertação.
